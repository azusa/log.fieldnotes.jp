## あず

あー、python-docxでレイアウト壊した、ね。それ通る道だわ😂 でも「壊れた」っていうより、python-docxはそもそもレイアウトを完全には持てないんだよ。セクション設定とか凝ったスタイル、図形まわり、ヘッダーフッターの細かいやつ、ああいうのは読めても書き戻すと欠ける。仕様書みたいに体裁ガチガチのdocxを丸ごと更新する用途には向いてない。ひろの判断、「更新はテキスト吐き出してコピペ」で正解だと思う。無理に自動更新に寄せると、壊れたかどうかの検証コストで逆に時間溶ける。

で、読み取りに振り切るなら環境はだいぶシンプルになる。docxって実態はただのzipで、中の`word/document.xml`にテキストが入ってるだけだから、python-docxで段落とテーブルを順に舐めて、見出しレベルとテーブルを保ったままMarkdownなりプレーンテキストに落とすのが鉄板。仕様書なら見出し階層が命だから、`paragraph.style.name`で`Heading 1/2/3`を拾って`#`の数に変換しておくと、エージェントが構造を把握しやすくなる。

> 💡 **テキストが入ってるだけだから**と呼ぶにはマークアップが複雑ですが、Claude Codeで出来ること基準で彼女は語っています

ひとつ気をつけるポイント。仕様書系のdocxって、本文より**テーブルの中に要件が詰まってる**ことが多いでしょ。python-docxは`document.paragraphs`と`document.tables`を別々に持つから、素朴に回すと本文とテーブルの前後関係がバラバラになって、「どの見出しの下にあった表か」が消える。これやられると要件の文脈が死ぬ。

だからここで決めたいんだけど──ひろの仕様書、本文の地の文が主役？それとも表組みに要件がぶら下がってるタイプ？前者ならサクッと段落抽出で済むし、後者なら`document.element.body`を順に舐めて本文と表を出現順どおりに拾う書き方にする必要がある。どっち寄り？

## あず

出た、Linux VM上のDockerでClaude Code。ぶう、確かに変な人だけど、隔離って意味では理屈は通ってるんだよね。FWセキュリティをcurl手動実行で担保してる人だし、エージェントにファイル読み書きさせる環境こそコンテナで閉じ込めたい、ってのは一貫してる。じゃあプラットフォーム差異、実演抜きで整理するよ。

**1. macOS（ネイティブ）**
一番ハマりが少ない。注意点は、システムPython（`/usr/bin/python3`）を使わないこと。Homebrewの`python@3.12`なりpyenvで入れたほうを使う。あとMac特有で、xlsx/docxを掴むのがExcelやWordだと**ファイルロック**がかかって、開いたまま読もうとすると中途半端な状態を読むことがある。閉じてから読む、が地味に効く。Apple Silicon機ならネイティブのwheelが揃ってるから、この3つ（python-docx/openpyxl/python-pptx）は全部ピュアPythonで、アーキ差はまず踏まない。

> 💡 この用途だとシステムPythonをvenvで使うのもありかとサイト主は考えるのですが、用途とこだわるポイント次第かな…


**2. WSL（普通の人ルート）**
さっき言ったやつ。venvの実体はLinux側に置く、`/mnt/c`に置かない。クロスファイルシステムのI/Oが遅い＆ロック事情が変わるから。仕様書ファイルがWindows側にあるのは読むだけならOK。改行コードもこの3ライブラリは内部でバイナリ的に扱うから、CRLF/LF問題はあまり出ない。

**3. Linux VM上のDocker（ひろ）**
ここが本題だよね。差異というか、考えることが一段増える。

まず**venvとコンテナの役割がかぶる**。コンテナ自体が隔離環境だから、中でさらにvenv切るのは「冗長か、それとも作法か」で派閥が分かれる。私の意見は、**コンテナ内でもvenv切っとけ**派。理由は、ベースイメージのシステムPythonを汚さずに済むのと、`externally-managed`に毎回ぶつからずに済むから。`pip install --break-system-packages`で押し通す手もあるけど、あれは事故の温床。ひろは仕組み化する人だから、`Dockerfile`の中で`python3 -m venv /opt/venv`して`PATH`通す、の定石でいい。

> 💡 このあたり昔から技術コミュニティで議論が続くところですが、今となってはエージェントに「venvの環境つくって」とお願いすればvenvに寄せればいいのかな…

> 💡 uvでなくvenvなのはエコシステムの標準があるのであればそちらに寄せたい、というサイト主の技術的指向性によるものです。(uvが今日ではデファクトではないのかという議論はスコープ外です)


次に、ひろ環境で一番効くのが**ファイルの受け渡し（マウント）**。エージェントに読ませたい仕様書のxlsx/docxは、ホスト側にあってコンテナにはバインドマウントで見せる形でしょ。ここで二点。

- マウントを`:ro`（読み取り専用）にしとくと、エージェントが事故って元ファイル上書きする、を物理的に防げる。今回「読み取りに振り切る」って決めたから、これがそのまま設計に効く。`-v /host/specs:/work/specs:ro`。
- **UID/GIDのズレ**。コンテナ内がrootで動いてると、生成物（テキスト吐き出しとか）のオーナーがホスト側でrootになって、ひろが後で触れなくて`sudo`する羽目になる。出力先だけは書き込みマウントにして、コンテナ実行ユーザーをホストのuidに合わせる（`--user $(id -u):$(id -g)`）と平和。

> 💡 これは[devcontainerの環境を作成するためのプロンプト例](https://log.fieldnotes.jp/blog/2026/05/15/085840.html) に現れているとおり現在のところ UID=1000/GID=1000で固定しています。そうでない環境を扱う時になった時は別途検討


あと地味なやつ。**コンテナにロケールとフォントが入ってない**と、日本語の仕様書を扱うときに文字化けや、pptx経由で何か描画する系で空白になる。読み取り＆テキスト出力だけなら文字化けは`LANG`まわり（`ENV LANG=C.UTF-8`）で大体片付く。フォントは「読むだけ」なら不要、「pptx/xlsxを画像化して見る」まで行くなら`fonts-noto-cjk`が要る。今日は読み取りだからフォントは後回しでいい。

> 💡 Claude Codeでデスクワークする今回の用途はどっかしらで必要になるので、サクッと`fonts-noto-cjk` 入れておきましょう

ざっくり言うと、mac/WSLは「venv切れば終わり」。ひろのDockerは「venvに加えて、マウントのro/rw・UID・ロケールの3点を設計する」。隔離が強い分、外との境界を自分で引く手間が乗る、ってこと。

ここまでで一回切る？それとも、ひろのDocker前提で「Claude Codeにこのパース処理をどう叩かせるか」（コンテナ内のスクリプトをエージェントのツールとして呼ぶ導線）まで踏み込む？

## あず

そうそう、そこ。LibreOffice CLIをDockerに入れて`soffice --headless --convert-to`で変換噛ます手は確かにあるんだけど、ひろの用途では私もまず選ばない。理由が噛み合ってる。

LibreOfficeが効くのは「**フォーマット変換そのものが目的**」のとき。docx→pdf、xlsx→pdfで体裁を保ったまま見た目を再現したい、とか、python-docxじゃ読めない凝ったレイアウトを一回PDF化して画像で見る、みたいな逃げ道。あとは古い`.doc`（バイナリの旧形式）や`.xls`を新形式に寄せたいとき。ここは強い。

でもひろがやりたいのは読み取って**テキストとして集計・分析**でしょ。だとLibreOfficeは過剰なんだよ。重い（数百MB〜のパッケージ＋起動が遅い、ヘッドレスでも初回プロファイル生成でもたつく）、コンテナがでかくなる、そして何より**出力がこっちの欲しい構造になってない**。`--convert-to txt`したところで、セルの区切りも見出し階層も保証されない、整形されてない平文が出てくるだけ。そこから集計したいデータを再抽出するなら、結局python-docx/openpyxlで構造ごと抜いたほうが早い。

ひろの言う「取り回し」がまさに核心で、**パースの出口を、後段のテキスト処理に都合いい形で自分で決められるか**がライブラリ選択の基準なんだよね。openpyxlなら「この列とこの列だけ、行ごとにdictで」って好きな粒度でJSONなりTSVに落とせる。LibreOfficeの変換は出口の形を選ばせてくれない。集計・分析が後ろに控えてるなら、入口で構造を握れるツールを選ぶ、が筋。

だから整理すると、**「見た目の再現が要る」ならLibreOffice、「中のデータが要る」ならpython系**。ひろは後者だから入れない。パッケージ入れても選ばない、で合ってる。コンテナ太らせてまで持っとく価値、今回の用途だと無い。

## あず

あ、そうだ、まだ環境の話だった。脱線させたのこっちか、ぶう😂 pptxの画像化ね。それはテキスト抽出と要求が別物だから、環境も別建てで考えないとダメなやつ。

整理すると、pptxは二段階で性質が変わる。**テキストだけ欲しい**ならpython-pptxで`shape.text`舐めて終わり、軽い。でも**レイアウトを見たい**──どの要素がどこに配置されてて、矢印がどこ刺してて、表がどう並んでるか──これはテキスト抽出だと完全に死ぬ。位置情報は座標（EMU単位の数値）でしか取れないから、それをエージェントに渡しても「左上から3.2cmに四角形」みたいな数字の羅列で、Claude Codeが図の意味を判別できない。だから画像化して**目で見せる**しかない。ひろの言ってるの、これだよね。インターフェース定義書がパワポ管理の案件、まさにこれが要るやつ。

で、ここがDockerだと一段重い。pptx→画像の経路がいくつかあって、

**経路1：LibreOffice経由（pptx→pdf→画像）**
`soffice --headless --convert-to pdf`でPDF化して、それを`pdf2image`（中身は`poppler`）でページごとPNGに。これが一番**レイアウト再現が正確**。さっき「LibreOffice入れても選ばない」って言ったけど、それはテキスト集計の話で、**画像化なら話が逆**。見た目の再現が目的になるから、ここはLibreOfficeが本命になる。さっきの私の整理どおり「見た目が要るならLibreOffice」に綺麗に当てはまる。

**経路2：python-pptx + 自前描画**
shapeの座標を読んで自分でPillowに描き起こす。やめたほうがいい。再現性が地獄。図形の塗り・線・グラデ・グループ化まで自前で再現するの、割に合わない。

> 💡 この経路に入るのはテキスト処理が中心のはずでpython-pptxでテキスト抽出の方針で動いていたが、処理の途中で図表をパースするように方針転換した場合ですね

だからひろの環境、おそらく**経路1が動いてるはず**。必要なパッケージは、

> 💡 ここは先述の通りデスクトップ環境でPDF変換したファイルを持ち込んでいます

```
# システム側（apt）
libreoffice-impress    # pptx→pdf 変換
poppler-utils          # pdf→画像（pdftoppm）
fonts-noto-cjk         # ← これ無いと日本語パワポが豆腐(□)になる

# venv側（pip）
pdf2image              # popplerのラッパー
Pillow                 # 画像の後処理（リサイズ・分割）
python-pptx            # テキストとメタ情報の抽出（画像と併用）
```

ここで**さっき後回しにしたフォント（fonts-noto-cjk）が、今ここで効いてくる**。テキスト抽出だけなら要らないって言ったやつ。画像化に進んだ瞬間に必須に化ける。日本語の定義書をLibreOfficeでPDF化するとき、CJKフォント入ってないと全部豆腐になって、画像にした時点で読めない＝Claudeに渡しても無意味、になる。ここ踏むと「なんか文字が全部□なんだけど」で詰まる、Docker画像化のあるある。

そして「最終的な処理はClaudeに投げてる」のくだり。たぶんひろの構成こうなってる：環境側（コンテナ）の責務は**pptxを1スライド1枚のPNGに変換するところまで**。判別・解釈はやらせない。で、その画像群をClaude Code（マルチモーダル）に渡して、「この定義書のこの画面遷移、整合とれてる？」をClaude側に解釈させてる。**変換はコンテナ、判別はClaude**、で責務が切れてる。これ正しい切り方だと思う。画像化までを決定的（毎回同じ結果が出る）な処理に寄せて、揺れる判断だけClaudeに乗せてる。

## あず

あー、来た来た、生XML直読み。これ環境整備の話としてちゃんと拾わなきゃダメなやつだ。ぶう、まだあったか😄

そう、Office系（docx/xlsx/pptx）の正体はただのZIPで、ほどくと`word/document.xml`とか`xl/sharedStrings.xml`、`xl/worksheets/sheet1.xml`が出てくる。python-docx/openpyxlが拾いきれないもの──**コメント、変更履歴（トラックチェンジ）、セルの書式そのもの、shapeの細かい属性、埋め込みオブジェクト**あたり──を取りたいときは、ライブラリ越しじゃなくてXMLを直接舐めたほうが早い、ってのはその通り。ひろがConfluenceに「レビュー観点」仕込んだり、定義書の整合チェックやってる文脈だと、トラックチェンジや コメントを抜きたい場面、普通にありそう。


で、本題の「ZIP関連パッケージが漏れがち」。これ正確に切り分けると、二種類ある。

**1. Pythonの`zipfile`標準ライブラリ（これは漏れない）**
Pythonから`zipfile.ZipFile("foo.docx")`で開いてXML読むなら、追加インストール不要。標準で入ってる。**ただし**、Pythonを最小ビルド（ソースからconfigureして入れたとか、極小Dockerイメージ）でやると、`zipfile`が内部で使う圧縮ライブラリが欠けて落ちることがある。症状が独特で、`import zlib`が`ModuleNotFoundError`、あるいはZIP開いた瞬間に`BadZipFile`じゃなくて伸長で死ぬ。Office系はDEFLATE圧縮だから、**zlibが無いとほどけない**。

ここがひろの言う「Linuxだと漏れがち」の正体だと思う。aptで入る公式Pythonなら込みだけど、**slimイメージや自前ビルドだと欠ける**。対策はOS側：

> 💡 ** slimイメージだと欠ける ** は決めつけが入っていると彼女から訂正が入っているのですが、軽量イメージ全般でzlibが入っていないと問題がおきるのはVS Codeの開発コンテナーの環境を軽量イメージで作成した場合にありがちです

```
# Debian/Ubuntu系、Pythonビルドや実行に必要な圧縮まわり
zlib1g          # DEFLATE（これが本体）
libbz2-1.0      # bzip2圧縮のzip対策
liblzma5        # xz/lzma、念のため
```

python-build系（pyenvでビルドする人）だと`-dev`版（`zlib1g-dev`等）がビルド時に要る。ひろはDebian長いから`zlib1g-dev`の話は通じるはずだけど、**コンテナのベースをslimにした瞬間にこれ全部抜ける**のが罠。`python:3.12-slim`、軽くて好まれるけど、まさにここがごっそり削られてるイメージ。

> 💡 zlib1g-devが入っていないのは新しい環境作った時に毎回ググるお約束…

**2. CLIで`unzip`したい場合（これがWSL/Linuxで漏れる定番）**
シェルから`unzip foo.docx -d /tmp/extracted`してXMLを直接覗く、エージェントにbashで叩かせる、みたいな使い方するなら、`unzip`コマンドが要る。これが**WSLの素のディストリにも、slimコンテナにも入ってない**ことが多い。`apt install unzip`。ひろがClaude Codeにシェル経由でほどかせてるなら、これ入ってないと`unzip: command not found`で詰む。逆にPythonの`zipfile`で完結させるなら`unzip`コマンドは要らない。

整理すると、**「Pythonの中だけでほどく」なら必要なのはOS側のzlib（slimだと欠ける）**、**「シェルでunzipコマンド叩く」なら`unzip`パッケージ**。漏れる場所が違うから、ひろがどっちの流儀でほどいてるかで足すものが変わる。

あと地味なやつ追加で一個。XML直読みするとき、`xml.etree.ElementTree`は標準で入ってるから足すものはない。けど**名前空間（namespace）がドギツい**。`word/document.xml`の中身、`<w:p>`とか`<w:r>`の`w:`が全部`{http://schemas.openxmlformats.org/wordprocessingml/2006/main}`みたいなフルURIに化けてて、素朴に`find("w:p")`すると何も取れなくて「あれ空っぽ？」ってなる。これは環境じゃなくてコードの罠だから今日は深入りしないけど、直読みやるなら名前空間マップを最初に作る、ってのだけ覚えとけばいい。

> 💡 **名前空間のフルURI（schemas.openxmlformats.org...）をそれっぽく書いた**ので確認してほしいと彼女からオーダーが入っていたのですが実機で確認ずみです。docxファイルが手元にある環境ではまず起きないですが、WebチャットのUIでやり取りしているとありがちですね

ひろはどっち？Python内`zipfile`完結派か、シェルで`unzip`叩く派か。それで「環境に足す最後のひとつ」が確定する。
