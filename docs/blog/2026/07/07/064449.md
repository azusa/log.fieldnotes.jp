# なぜGitHub Actionsの通知はチームに同報できないのか

## はじめに

GitHub Actionsのワークフロー実行結果（成功/失敗）の通知は、GitHub本体の通知システムに乗って配信されます。Actions専用の通知チャネルがあるわけではなく、Issue・PR・Discussionなどと同じ仕組みを共有しています。

GitHubはOSSの開発を想定して送信される通知を受け取る側の開発者が購読・フィルタリングする想定の通知設計となっており、業務開発を想定したチーム内に通知を同報した作りになっていません。

実際、通知の制御は個人アカウントのWatch設定やNotification設定に紐づいており、リポジトリ管理者が「このチームに同報する」といった配信制御を標準機能として持っていません。

このことはGitHub自体はドキュメントやブログで公言していることではありませんが、GitHubの設定画面からはそのような設計思想が読み取れます。

## Actionsのデフォルトの通知設定

Actionsのデフォルトでは、自分がトリガーした実行（手動実行、自分のpush起因など）が完了したときに通知が飛びます。デフォルトでは失敗時のみですが、成功も含めて毎回受け取る設定も選べます。

また、ユーザーに通知されるのは、あくまでユーザ側がNotificationsの設定で通知を受け取る設定にしていた場合です。通知の出し分けは、原則として受け取る各ユーザーが自分の設定でやるものです。

- Settings → Notifications で、Actionsの通知を「メール / Web / オフ」から選択
	- 「失敗時のみ」か「毎回」かを選択
- リポジトリ単位の Watch設定（All Activity / Participating / Ignore など）で受信範囲を調整
- メールクライアント側のフィルタルール（差出人・件名・ヘッダで振り分け）

GitHubはActionsの通知メールに識別用のヘッダを付けているので、メールクライアント側でのルール振り分けは現実的な選択肢となります。

## カスタマイズによる通知実装

「特定のチャネルに送りたい」「成否で宛先を変えたい」「フォーマットを整えたい」といった要件がある場合は、標準通知によらずに自前の仕組みを実装する必要があります。代表的な方法は以下の通りです。

### ワークフロー内から直接送信

ジョブのステップで、Slack / Teams / メール送信のアクションを呼びます。if: failure() などの条件で送信を制御でき、宛先も本文も自由です	。最も手軽で、案件でよく採用されるパターンですが、ビルドの処理内に案件に応じた通知処理を作り込むので、ワークフローの汎用性は失われます。

### Actions から Pull Request / Issue にコメントする
Actions 内から GitHub CLI（gh）を使って Pull Request や Issue にコメントし、間接的に通知する方法です。コメント本文にメンションを付与でき、Organization 内の Team を指定すればチームへの同報も実現できます。外部サービスへの連携を挟まず GitHub 内で完結するため、標準の通知システム（受け手側での購読・フィルタ）にそのまま乗せられるのが利点です。

### Webhook / repository_dispatch で外部に流す

実行結果を外部システムが受けて、そこで振り分け・整形・再配信します。配信ロジックを一箇所に集約したい場合に向きます。組織のセキュリティーポリシーでGitHubの外部への送信に条件がある場合は、ポリシーとのすりあわせが必要です。

## 最後に

いずれも「GitHubの標準通知では届かない要件」を満たすための追加実装であり、実装、運用ともそのためのコストが発生します。GitHubの標準の通知の受け取りに対するルール化で処理できるのであれば、まずその範囲でスタートし、追加で発生した要件に対し最小限の実装で対応することをおすすめします。
